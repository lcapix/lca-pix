# LCAPIX test plan: API, authz, database, E2E and security

How the next phase tests the flows in [USER_FLOWS.md](USER_FLOWS.md), driven by [flows.yaml](flows.yaml) and [PERMISSIONS_MATRIX.md](PERMISSIONS_MATRIX.md).

- **Baseline:** branch `v1-hardening-kavish` @ `704a964`. Starting numbers: 292 Vitest tests passing and 5 skipped; 46 `tsc` errors; no route, page or E2E tests beyond the mocked ones in `tests/api/**`.
- **Where the branch is now:** it moved to `c4a7200` while this plan was written, with **fix/authz, fix/platform, fix/auth and fix/runs merged**. fix/editor and fix/factors are still open.
  - Start `tests/authz/merged-fixes.json` with those four branches.
  - Every expected-fail below whose ID appears in `flows.yaml#merged_fixes` should then be asserted as **passing**. If it fails, it is a regression to report, not a known bug.
  - fix/platform already delivered part of this plan: the lazy env-only DB pool, security headers, the xlsx replacement, and CI checks on PRs. Build on those rather than duplicating them.

## 0. Ground rules (non-negotiable)

1. **Localhost only.**
   - Every suite runs against `127.0.0.1` or `localhost`: MySQL on `127.0.0.1:3307` and the app on `http://localhost:3002`.
   - Nothing contacts RDS, `lca-pix.vercel.app`, `lcapix.vercel.app` or `lca-project-v3.vercel.app`. The older guides (`docs/E2E_TEST_GUIDE.md`, `docs/SAMPLE_CASE.md`) target production; reuse their **data**, never their URLs or credentials.
2. **Guard before connecting.**
   - `lib/db.ts` falls back to the production RDS host when `DATABASE_HOST` is unset, and it opens a connection **at import time**.
   - Every suite's setup must therefore call `tests/support/assert-local-db.ts` **before** anything imports `lib/db`. The guard aborts unless:
     - `DATABASE_HOST ∈ {127.0.0.1, localhost, ::1}`,
     - `DATABASE_NAME` matches `/^lca_test(_\w+)?$/`,
     - and `DATABASE_USER` is not `lcaadmin`.
   - Playwright `globalSetup` runs the same check before it starts the web server.
3. **No root scripts.** Do not run any root `*.sh`/`*.js`. Several of them reach live databases or run `DROP TABLE` (audit M8).
4. **Secrets.**
   - Test credentials are generated by fixtures, or live in `.env.test.local` (gitignored).
   - Committed placeholders go in `.env.test.example`.
   - Test output never prints them.
5. **Known bugs are encoded, not worked around.**
   - A test for a known defect asserts the **intended** behaviour and is marked expected-to-fail with the audit ID and the branch that fixes it. Vitest uses `it.fails`; Playwright uses `test.fail()` / `test.fixme()`.
   - When a fix merges, the marker flips, and CI fails if an expected-fail test starts passing (Vitest `it.fails` does this natively).
6. **Toasts are invisible** until the design work (P01) mounts a `<Toaster/>` (X-UI-1). E2E tests assert on network responses, the URL, inline text and DOM state, never on toast text. Toast assertions are `test.fixme('X-UI-1')`.

**Route-coverage guard** (`tests/authz/route-coverage.test.ts`):
- Globs `app/api/**/route.ts` and regex-extracts the exported handler names (`export (async )?function (GET|POST|PUT|PATCH|DELETE)` and `export const …`).
- Fails if any route × method is missing from `flows.yaml#permissions`, or if the matrix lists one the code doesn't export.
- This is what keeps the matrix honest as routes are added (e.g. `POST /api/auth/logout` from fix/auth).

## 2. (a) API integration tests against a real local MySQL

### 2.1 Tooling
- **Runner:** Vitest 4 (already installed), in a separate config `vitest.int.config.ts` with:
  - `environment: 'node'`, `include: ['tests/int/**/*.test.ts']`
  - `pool: 'forks'`, `poolOptions.forks.singleFork: false`, `fileParallelism: true`, `testTimeout: 30000`
  - `setupFiles: ['tests/support/assert-local-db.ts', 'tests/support/int-setup.ts']`
- **Database:** MySQL **8.0**, the same major version as RDS (confirm the exact minor on the RDS console before pinning). Run it with the `docker-compose.local.yml` service planned in design P00 §1 (`127.0.0.1:3307`) or `@testcontainers/mysql` in CI.
- **Libraries:**
  - `mysql2` (existing) for fixtures and assertions.
  - `yaml` (new devDependency) to read `flows.yaml`.
  - `zod` (existing) for response-shape contracts in `tests/support/contracts.ts`.
  - `msw@2` (new devDependency) for outbound HTTP (§7).

### 2.2 How a test calls the API
- Import the handler and call it directly. This is the same pattern the existing `tests/api/**` use, but **without** mocking `@/lib/auth` or `@/lib/db-helpers`:
  ```ts
  import { POST } from '@/app/api/cases/[caseId]/components/route'
  const res = await POST(
    new NextRequest(`http://localhost/api/cases/${caseId}/components`, {
      method: 'POST',
      headers: { Authorization: `Bearer ${tok.editor}`, 'Content-Type': 'application/json' },
      body: JSON.stringify({ component_name: 'Forming Line', component_type: 'machine_line', parent_component_id: productId }),
    }),
    { params: Promise.resolve({ caseId: String(caseId) }) },
  )
  expect(res.status).toBe(201)
  ```
- **Tokens:** mint them with `createToken({id, email, account_type})` from `lib/auth.ts`, using the test `JWT_SECRET` (`tests/setup.ts` already sets `test-secret-do-not-use-in-prod`). F1/F2 get tokens through the real signup and login routes instead.
- **DB side effects:** assert them with direct `SELECT`s through a separate `mysql2` connection (`tests/support/db.ts`). Never assert them through the API under test.
- **Handler-level vs HTTP:**
  - A small **HTTP smoke layer** (`tests/int/http/*.test.ts`) runs against `next start` for what only the server stack shows: `next.config` headers, streaming (`/api/insights`), multipart size handling, and cookies set by `/api/auth/google`.
  - Everything else stays handler-level for speed.

### 2.3 Isolation strategy
- **A per-test transaction with rollback is not viable.** Route code uses `pool.execute` on whatever pooled connection is free. `lib/db-helpers.transaction()` then opens its own connection and issues `BEGIN`/`COMMIT`, so no outer transaction can contain it.
- Instead:
  1. **One database per Vitest worker:** `lca_test_w${VITEST_POOL_ID}`. The worker's `DATABASE_NAME` is set **before** `lib/db` is first imported, in `int-setup.ts` via `process.env`, and the pool is closed in `afterAll(() => pool.end())`.
  2. At worker start, create the DB from the **baseline schema** and **reference seed** (§4.1). That takes a few seconds with `mysql < file`.
  3. `beforeEach` at file level **truncates tenant tables** with `SET FOREIGN_KEY_CHECKS=0`, then restores the check:
     - `account`, `project`, `project_members`, `case_table`, `component`, `flows`, `assessment_runs`, `assessment_results`, `case_documents`, `comparison_runs`, `comparison_results`, `comparison_metadata`, `integration_log`, `cost_rates`
     - plus custom rows in `substances`, `driver_impact_factors` and `process_templates` (`is_custom=1`, or `created_by IS NOT NULL`).
  4. Reference tables are never mutated, except by the integrations tests. Those run in their own worker (a `sequence.groupOrder` group) and re-seed afterwards.
- **Fixture builder** (`tests/support/world.ts`) creates the **standard world** through the API, with SQL only where no API exists:

| Handle | How | Notes |
|---|---|---|
| `owner` / `editor` / `viewer` / `adminm` / `nonmem` / `userB` | `POST /api/auth/signup`, then `PUT /api/auth/profile` | unique emails per test run |

## 3. (b) Authz matrix tests (generated)

- **Source:** `flows.yaml#permissions`, one entry per matrix row. Each entry carries `method`, `path` (with `$handles`), `sample_body`, `expect` (role → status or list of accepted statuses), and optional `now` (role → current status), `tag` and `fixed_by`.
- **Generator:** `tests/authz/matrix.test.ts` builds a `describe.each` over rows × roles, adding `deactivated` and `tampered` to every non-public row. No code generation step is needed; the YAML is read at collection time.
- **Resource freshness:** for state-changing rows (every non-GET), `arrange()` builds a **fresh** resource per role, so one role's 200 can't destroy the next role's target. For example, each role gets its own `DELETE /api/projects/:id` target project, owned by `owner`, with the same memberships.
- **Assertions:**
  - `expect(res.status).toBe(row.expect[role])`, or `toContain` when the value is a list (D3 accepts `[403, 404]` for NonMem/PAdmin).
  - For 2xx on write rows, also assert the DB changed. For 4xx, assert it did **not**, by comparing a table-scoped checksum before and after.
- **Current-vs-intended:** when `row.now[role]` exists and `row.fixed_by` has not merged (tracked in `tests/authz/merged-fixes.json`), the case is wrapped in `it.fails`.
- **Cross-tenant sweep** (`tests/authz/cross-tenant.test.ts`): for every row whose path has an id, userB calls it with P's ids, and P's owner calls it with Q's ids. Expected `{403, 404}`, never 2xx, and a response body without P's or Q's names.
- **Body-borne ids,** which the path-based matrix can't see:
  - `parent_component_id` from Q (M1)
  - `substance_id` of B's custom substance (L3)
  - `sourceCaseId` from Q (clone-from)
  - `attach_component_id` from another case (ingest/apply)
  - `runs=` overrides naming another project's run (compare)
  - `case_ids` from Q (legacy comparisons)

## 4. (c) Database tests

Suite: `tests/db/**`, run with `vitest.db.config.ts`, single worker (the tests create and drop whole databases).

### 4.1 Building a schema from nothing (a prerequisite, and a known gap)
The repo cannot build its own schema today:
- `lca_v3_drawsql_schema.sql` is stale. It has `project_members.account_id` where the code uses `user_id`, and `driver_impact_factors.driver_name/geographic_region` where the code uses `substance_id/geographic_scope/method_name`.
- The `account` profile columns (`full_name`, `company`, `role`, `use_case`, `country`, `onboarded_at`) come from **no migration** (AUTH-7).
- Migrations live in two directories with no ledger. 014/018/020/021/022 need the `mysql` CLI because they use `DELIMITER`.

**Plan:**
1. **Baseline** `db/baseline/000_schema.sql`: `mysqldump --no-data --routines=false --triggers` of the **local** DB built in design P00 §1 (dev dump + 009–025). Review it, strip `DEFINER`s and `AUTO_INCREMENT` values, and commit **structure only**.
2. **Reference seed** `db/baseline/001_reference.sql`, kept small and reviewable:
   - `permissions` (owner/admin/editor/viewer)
   - `impact_categories`
   - the substances and factors the fixtures and golden tests need: Electricity (US eGRID + Global Ember), Natural Gas, Steel, Aluminum, Argon, Nitrogen, CO2, Methane, Nitrous oxide, Wood, Coal, and one ozone-depleting substance for the precision test
   - the 023 process templates
   - one QUARANTINE row per method (for the E2 test)
   - Generate it with a reviewed `SELECT … INTO` script, not by hand.
3. **Runner** (fix-first/§5 of the audit): a ~30-line `scripts/db/migrate.mjs` that applies files in order through the `mysql` CLI and records them in `schema_migrations(filename, checksum, applied_at)`. It refuses non-local hosts using the same guard.

### 4.2 Migrations apply-twice

`tests/db/migrations-idempotent.test.ts`:
1. Create an empty `lca_test_migrate`.
2. Apply `000_schema.sql` with the 009–025 effects removed, **or**, where the runner exists, the pre-009 baseline. Then apply `001_reference.sql`, then `migrate-009` … `migrate-025` in numeric order.
3. Snapshot the schema:
   - `information_schema.COLUMNS` (name, type, nullability, default)
   - `STATISTICS` (indexes)
   - `KEY_COLUMN_USAGE` + `REFERENTIAL_CONSTRAINTS` (FKs, `ON DELETE`)
   - plus row counts and checksums (`CHECKSUM TABLE`) of the reference tables.
4. Apply 009–025 **again** and re-snapshot. Assert **no schema diff**, with reference-data diffs limited to an explicit allowlist.
5. Mark the known failures as expected-fail with IDs:
   - `database/migrations/008` bare `DROP INDEX` (not idempotent)
   - the duplicate `002_` prefix
   - `005` vs `010` column churn
   - 009 after 015 changes TRACI methane 25→28 (E5)
   - 016 overwriting the Wood fuel factor (E1)
6. The same test also asserts the DB has **no** `DELIMITER`-dependent failure when run through the runner (§4.1).

### 4.4 Snapshot immutability (RUN-1, EXP-1, STAGE-2)
`tests/db/run-snapshot-immutable.test.ts`:
1. Run `$P.base`, then capture four things:
   - `GET /api/assessments/:run` (totals, `component_breakdown`)
   - `GET /api/cases/:base/assessments` for that run (`impacts`, `componentBreakdown`, `flowDetail`)
   - the CSV export rows
   - the stage split
2. Mutate the case in three ways: rename a step; change a flow quantity; set a different `life_cycle_stage`.
3. Then `DELETE /api/components/:id` a leaf that carries a flow.
4. Re-read all four. They must be **byte-equal** to the captured values: totals, per-step rows, names, stages, and the CSV. Expected-fail (RUN-1, STAGE-2, EXP-1) until fix/runs.
5. Assert the FK `assessment_results.component_id` is `ON DELETE SET NULL`, or that the per-step rows live in `run_snapshot`, whichever design fix/runs picks.

### 4.5 Precision (DOUBLE)
- **Column type:** `information_schema.COLUMNS` for `assessment_results.impact_value` must be `double`, via a new migration (RUN-2). Expected-fail until fix/runs.
- **Round trip:**
  1. Seed an ozone-depletion factor for a fixture substance (e.g. 0.5 kg CFC-11 eq/kg for a test halon), and a flow of 8.4e-9 kg on a leaf.
  2. Run the assessment.
  3. `SELECT impact_value` must equal the engine value (4.2e-9) within a relative 1e-12.
  4. `GET /api/assessments/:run` must return a non-zero value.
  5. The results page must not show 0 (checked in E2E F9).
- **Flows quantity:** `flows.quantity` is `DECIMAL(15,6)`. A POST with `quantity: 0.0000004` stores 0. Decide DOUBLE or DECIMAL(24,12) (not in the audit's fix list; raise it). ING-1 is the import-side twin (rounding in `maplca.ts`).
- **Engine-level:** keep `tests/lib/lca-engine.test.ts`. Also run `tests/e2e-local/engine-golden.local.test.ts` with `LOCAL_DB=1` against the test DB in this suite.

### 4.6 Atomicity
Inject a failure by pointing a later statement at a missing column in a scratch DB, or by wrapping the `conn.query` spy. Assert no partial rows remain for:
- `ingest/apply` (create and append), which is transactional and must leave nothing behind
- `duplicate` (transactional)
- `scale` (transactional)
- `POST /api/projects`, the example project and `clone-from`: non-transactional (PROJ-2, CMP-2), so expected-fail.

## 5. (d) Playwright E2E (localhost only)

### 5.1 Setup
- **Packages:** add `@playwright/test`. The repo has only the `playwright` library (`^1.49.0`). Design P00 §2 already plans this config, so share it:
  - `webServer`: `pnpm build && pnpm start -p 3002` in CI, or `pnpm dev` locally, with `.env.test` loaded.
  - `baseURL: 'http://localhost:3002'`
  - `use: { trace: 'retain-on-failure', reducedMotion: 'reduce', timezoneId: 'UTC', locale: 'en-US', viewport: { width: 1440, height: 900 } }`
  - `retries: process.env.CI ? 1 : 0`, `workers: 2` (each worker gets its own `lca_test_e2e_w{n}` DB and its own server port).
  - Chromium only at first.
- **Network lock:** `context.route('**/*', r => isLocal(r.request().url()) ? r.continue() : r.abort())`, except `accounts.google.com`, which F3 fulfils itself.
- **Auth state:**
  - `globalSetup` signs up the world users through the API.
  - Per role it writes a `storageState` with `localStorage` keys `auth_token` and `user`, **and** the Zustand key `lcapix-auth = {"state":{"user":{…},"isAuthenticated":true},"version":0}`, because `AuthGuard` only reads the Zustand flag.
  - Routes that need a fresh user (F1, F3) start with an empty state.
- **API calls from the page** carry `?_t=<timestamp>` (`lib/api-client.ts:71-73`), so `page.waitForResponse` predicates match on `url.pathname`, not the full URL.
- **Seeding:** every spec seeds through the API (`tests/e2e/support/api.ts`, reusing `tests/support/world.ts`) with names suffixed by `testInfo.workerIndex` and `Date.now()`. No UI-driven setup except in the flow under test.
- **Selectors,** in order of preference:
  1. role + accessible name
  2. `#id` (login/signup `#email` `#password` `#fullName`; new project `#projectName` `#functionalUnit` `#boundary` `#methodology` `#region`; case forms `#caseName` `#caseDescription` `#baseCaseId`)
